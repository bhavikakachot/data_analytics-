## Ranking Delivery Agents Within Each City

The two window functions I would use are:

- `RANK()` to assign each agent a rank within their city based on completed deliveries.
- `LAG()` to retrieve the completed-delivery count from the preceding agent in that city's ranking order.

The counts should be calculated before applying the window functions, so I would use a common table expression:

```sql
WITH monthly_counts AS (
	SELECT
		agent_id,
		agent_name,
		city,
		COUNT(*) AS completed_deliveries
	FROM deliveries
	WHERE status = 'completed'
	  AND delivered_at >= DATE_TRUNC('month', CURRENT_DATE)
	  AND delivered_at < DATE_TRUNC('month', CURRENT_DATE) + INTERVAL '1 month'
	GROUP BY agent_id, agent_name, city
)
SELECT
	agent_id,
	agent_name,
	city,
	completed_deliveries,
	RANK() OVER (
		PARTITION BY city
		ORDER BY completed_deliveries DESC
	) AS city_rank,
	LAG(completed_deliveries) OVER (
		PARTITION BY city
		ORDER BY completed_deliveries DESC, agent_id
	) AS previous_agent_count,
	completed_deliveries - LAG(completed_deliveries) OVER (
		PARTITION BY city
		ORDER BY completed_deliveries DESC, agent_id
	) AS difference_from_previous
FROM monthly_counts
ORDER BY city, city_rank, agent_id;
```

`PARTITION BY city` restarts both the ranking and the previous-row calculation for every city. `ORDER BY completed_deliveries DESC` puts the highest-performing agent first, so `LAG` returns the count for the agent directly above the current agent. The first agent in each city has no previous row, so its `LAG` value and difference are `NULL`. `RANK` gives tied agents the same rank and leaves gaps after a tie; `DENSE_RANK` could be substituted if consecutive ranks are required.

Window functions are more accurate and maintainable here because they calculate rankings and adjacent-row comparisons while preserving one result row per agent. A `GROUP BY` alone can calculate counts, but it cannot naturally identify each agent's position or the preceding ranked row. A self-join or correlated subquery would need to recreate ordering logic manually, handle ties and city boundaries explicitly, and may generate duplicate or incorrect matches. The partition and ordering rules are declared once in the window expressions, making the intended city-specific ranking easier to read, test, and change.
