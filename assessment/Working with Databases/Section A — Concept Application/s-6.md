## CTE Versus Nested Subquery

A CTE makes the two stages explicit: first calculate the five categories with the most orders, then use that result to filter the detailed orders.

```sql
WITH top_categories AS (
	SELECT restaurant_category
	FROM orders
	GROUP BY restaurant_category
	ORDER BY COUNT(*) DESC
	LIMIT 5
)
SELECT o.*
FROM orders AS o
JOIN top_categories AS tc
	ON tc.restaurant_category = o.restaurant_category;
```

The equivalent nested-subquery version is:

```sql
SELECT o.*
FROM orders AS o
WHERE o.restaurant_category IN (
	SELECT restaurant_category
	FROM orders
	GROUP BY restaurant_category
	ORDER BY COUNT(*) DESC
	LIMIT 5
);
```

### Trade-offs

- **Readability:** The CTE gives the intermediate result a meaningful name and separates the ranking logic from the detail retrieval. This is easier to scan than a deeply nested `WHERE` clause. A short nested subquery can still be very readable when it is used only once.
- **Reuse:** A CTE can be referenced by multiple later statements within the same query. For example, `top_categories` could be joined to orders and also joined to category-level summary data without repeating the top-five logic. A nested subquery normally has to be duplicated if the same intermediate result is needed in several places.
- **Debuggability:** The CTE can be run independently by selecting from `top_categories`, making it easy to verify the five categories and their counts before checking the final detail query. With a nested subquery, the developer must extract or mentally isolate the inner query to inspect it.
- **Performance:** A CTE is not automatically faster than a nested subquery. Depending on the database and version, the optimizer may inline the CTE or materialize it. Execution plans should be checked when performance matters. Both forms express the same filtering requirement, although a join or `IN` may have different optimizer behavior in a particular database.

I would prefer the nested subquery when the intermediate result is used only once and the condition is short and local, such as this single `IN` filter. In that specific situation, introducing a CTE would add a separate named section without improving reuse or making the query materially easier to understand. I would choose the CTE once the top-five logic is complex, reused, or likely to be debugged independently.
